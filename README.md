**Задание 1. СУБД**
1.1 Реляционная СУБД, как PostgreSQL или MySQL. Они дают четкую структуру через таблицы, ACID-транзакции для целостности — это важно для финансов, где данные должны быть согласованными и защищенными от потерь.
1.2 Для лендингов с лидами — документо-ориентированная NoSQL, как MongoDB: гибкая, без схем, хранит данные как документы с ключами-значениями, быстро на запись/чтение.
1.3 Для базы норм и материалов — реляционная, как PostgreSQL. Простая структура с таблицами по иерархии компании.
1.4 Для маршрутов и распределения — графовая NoSQL, как Neo4j: работает с узлами, быстро находит пути.

**Задание 3. SQL vs NoSQL**
3.1 Пять преимуществ SQL (реляционных) над NoSQL:

Жесткие схемы для целостности данных.
ACID-транзакции для надежности в операциях.
Стандартный SQL для простых запросов и миграций.
Джойны для связей между таблицами.
Зрелые инструменты для безопасности и бэкапов.

Задание 4. Кластеры
NoSQL, например, MongoDB, потому что она
Хорошо работает с большими данными — делит их на куски (шардинг) и распределяет по машинам.
Не падает, если часть серверов недоступна CAP устойчивость
Быстрая для вычислений, так как не требует строгой структуры, как SQL, и может работать с данными "на лету".
Поддерживает принцип BASE — система всегда отвечает, даже если данные не сразу синхронизируются.

Для вычислений лучше использовать Spark — он быстрее,держит данные в памяти, а не пишет на диск. Это позволяет быстро обрабатывать кучу данных на всех 1000 машинах, даже если что-то пойдёт не так.
